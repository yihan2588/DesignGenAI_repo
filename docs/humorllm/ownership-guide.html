01 / What makes this more than an image description?

A cat is asleep on a laptop. Where is the joke?

First, inspect the scene below. Compare “A cat is sleeping on a keyboard” with “Perfect attendance. Questionable contribution.” What did the second caption add? You can answer from the scene alone; you do not need humor theory yet.

Try before reading

“Perfect attendance.
Questionable contribution.”

The image supplies physical presence and sleep. The caption borrows the language of workplace performance. “Attendance” fits being there; “contribution” clashes with doing nothing.

The joke creates a second reading of the same evidence. It lets the viewer connect the cat's behavior to a familiar human situation.

The hypothesis behind the project

HumorLLM tries to make that move more deliberate. A script is a familiar account of what happens in a situation: for example, people at a work computer are expected to work. Script opposition places two incompatible readings together: being present versus being productive. This is a useful humor design lens. A mismatch alone does not guarantee a laugh; the viewer must understand the connection and find it worthwhile.

Grounding means that the caption's key premise connects to visible evidence. Here the cat really is asleep on a keyboard. An invented analogy can work because the image supports the relation. A claim that “the manager rejected my promotion yesterday” requires an unseen event, so the viewer has to supply much more of the joke.

Explore the distinction

Change the caption. Which part of the mechanism survives?

Grounded comic analogy: physical presence versus useful work.

Worked comparison: “Perfect attendance. Questionable contribution” maps sleep on a keyboard to low workplace contribution. “Mood” offers a broad reaction with little image detail. “My manager rejected my promotion yesterday” adds a specific event absent from the scene.

These judgments explain the teaching examples. Actual audience preference can differ.

A large language model (LLM) generates text from learned patterns and the current input. Its direct answer may already be good. The project's hypothesis is that explicit visual facts, competing interpretations, and several candidate captions will make a useful comic connection easier to find. Each step can also fail: bad observations propagate; a forced conflict can feel contrived; self-selection can favor a bland caption.

02 / The smallest complete generation experiment

One shared image, two independent approaches.

Each comparison uses the same prepared image, model ID, audience, language, and style guidance. The baseline is the simple method used as a reference. It gets a direct caption prompt. The guided branch first makes a visual plan, then generates and chooses among three captions. Both final captions must pass validation before either is published.

Predict: can the candidate call start before the plan finishes?

No: it needs the validated plan. The baseline can run during both guided calls.

Guided branchImage → call 2: plan → call 3: candidates + selectionThe image is sent again with the plan.
1 / 5

Start the two branches

Baseline and planning begin concurrently. Normal call budget: three.

Complete trace, including the publication boundary
  1. Start the direct-caption request and the visual-planning request concurrently.
  2. Validate the plan. It contains neutral image metadata, 1–5 detail IDs, 1–2 conflicts, and exactly three angles that reference those IDs.
  3. Send the same image and the validated plan to the candidate call. Validate exactly three distinct captions and a valid selected_id.
  4. Wait for both branches. Reject identical final captions after normalization; use the spare attempt for a replacement when available.
  5. Save the metadata, private method mapping, and both captions in one database transaction. The run becomes ready only when that save succeeds.

What validation can establish

parsePlan rejects repeated detail IDs and angles that reference absent IDs. parseCandidates requires three unique candidate IDs, three captions distinct after normalization, valid detail references, and a selected ID in that set. Normalization removes punctuation and spacing and folds case, so punctuation changes do not create a new caption.

A candidate can reference a real ID while still inventing a story. The parser checks that d1 exists; it cannot see whether the observation behind d1 is true or whether the joke uses it correctly. Visual inspection and later relevance judgments remain necessary. Also, three distinct strings can use the same comic angle; semantic diversity is currently a prompt request.

Normal calls = 1 baseline + 1 plan + 1 candidate/selection = 3
Ideal branch time ≈ max(tbaseline, tplan + tcandidates)

The time expression assumes the branches overlap and ignores preparation, network, retries, trace writes, and the final save. For hypothetical call times of 2, 3, and 4 seconds, the branch time is about 7 seconds, versus 9 seconds if all calls were sequential. These are illustrative times.

generatePair has a 90-second pipeline deadline, a per-call timeout of at most 45 seconds, and a shared ceiling of four provider attempts. One malformed output may consume the extra attempt. A final duplicate may also need it. If the allowance or time is exhausted, the run fails explicitly. Client/configuration errors such as a quota response do not get an automatic retry.

03 / The implementation you can trace

Follow one upload through the system.

The current app uses Next.js, the framework that serves pages and server handlers; React, which builds the interface; and TypeScript, which adds checked types to JavaScript. Supabase provides sign-in, Postgres records, and image storage. Google Gemini processes the image. Vercel hosts the request-bound application.

1. Prepare bytes before the request can be rejected

UploadForm calls prepareUploadImage in the browser. It accepts nonempty JPEG, PNG, or WebP sources up to 50 MiB. If a source exceeds 2 MiB or its longest side exceeds 1,600 pixels, the browser resizes and converts it to a bounded JPEG. This keeps the upload below the configured 3 MB Server Action body limit.

The server then independently calls prepareGalleryImage. Sharp, an image decoder and transformer, checks the true format, rejects animated/malformed images and inputs beyond its 20-million-pixel decode bound, applies orientation, re-encodes to JPEG, and drops camera metadata. The server output is bounded at 2 MiB and a 2,000-pixel bounding box. Before Gemini, the generation route creates a separate JPEG with a 1,200-pixel bounding box at quality 85. Both caption methods receive those same bytes.

The three sizes serve different boundaries: browser transport, authoritative server validation, and provider input. Client preparation improves usability; a direct caller can bypass it, so server validation remains essential. “MiB” means 1,048,576 bytes; the UI labels these limits as MB.

2. Create a recoverable pending run

uploadHumor requires a verified user with a complete profile and a public-sharing acknowledgment. It saves one sanitized image under the user's path in humor-images, then calls humor_create_upload. A remote procedure call (RPC) invokes a named database function. That function creates the image record and pending run together, using placeholder metadata until analysis succeeds.

An idempotency key is a request ID reused when the same logical submission is retried. Unique (owner_id, request_key) prevents multiple run records for that ID. The action first looks up an existing run. Database constraints and checked functions are the final protection against races; they are stronger than disabling a button. Storage and Postgres are separate operations, so a database-create failure needs object cleanup. A process crash can still leave an unattached object.

3. Authorize and claim generation

POST /api/humor/runs/[id]/generate checks the request origin, verified session, run ID, and ownership. A same-origin check helps reject unwanted cross-site requests; ownership stops one signed-in user from generating another user's run. It then calls humor_claim with the server-only writer key.

A claim atomically changes a pending run to generating and returns an attempt token. A duplicate caller gets no fresh token. Every stage write and successful finish checks that token and the run state, so an old attempt cannot overwrite a newer result. The database claim window is 105 seconds; the route declares a 120-second maximum duration. Those are checked-in settings, not measured completion promises or proof of the deployment's runtime configuration.

Understand the writer key and the quotas

The implementation uses HUMOR_WRITER_KEY, plus the user's session. The database stores a SHA-256 hash, a one-way digest of the key, in private.humor_config. Checked generation functions compare the supplied key's digest, verify auth.uid(), and restrict the run to its owner. This is a scoped application credential, different from the service-role approach proposed in the MVP plan.

The server also needs GEMINI_API_KEY, SUPABASE_URL, and SUPABASE_ANON_KEY. Keep the writer and provider keys out of browser bundles and logs.

Database functions enforce one new upload/retry per 30 seconds and ten non-example runs per user in a rolling 24-hour window. The project configuration defaults to 100 claimed runs per rolling day; the implementation counts recent generation deadlines. Administrator-marked examples skip the member ten-run allowance, but still count for cooldown and project generation. These counts bound access, not dollars. A dollar budget needs usage records and conservative reservation before spending.

4. Await, record, and publish atomically

The route awaits generatePair. Each completed or failed stage is sent to humor_record_step with prompt, output or bounded diagnostic, usage when returned, and elapsed milliseconds. This makes a failure explainable: did extraction invent an object, did parsing fail, or did the provider return a quota error?

humor_finish uses a transaction: related database writes either commit together or roll back together. It saves generated metadata, the private result and random method-to-slot mapping, and both public captions. Only then does the run become ready. If a branch fails, the owner sees a failed attempt and the saved image remains available for retry. There is no half-comparison in the public feed.

pendingImage saved; generation not claimed.
→
generatingOne claimed attempt; deadline and token.
→
ready / failedBoth captions saved, or a truthful error.

A ready pair is immutable: the database trigger prevents changes to its captions, image, or ready state. Votes therefore continue to refer to the exact pair that users saw. A retry creates a new run linked by parent_id and reuses the saved image. An expired generating attempt becomes failed during the checked retry path after the deadline plus a 15-second grace period; there is no separate stored “interrupted” status.

This MVP has no durable worker. A terminated hosting request can leave a generating row until recovery. The browser's progress view offers generation/retry and refresh; an owner-only status endpoint also exists. It does not continuously resume work in the background.

04 / The experiment is also an access-control problem

Only a saved first choice unlocks the poll.

People can be influenced by method names and existing results. The app therefore uses neutral A/B labels before voting, assigns methods to slots randomly once per run, and hides counts and method labels until a vote commits. This reduces two avoidable sources of bias. It does not make a self-selected public poll a controlled study.

RecordStoresWho reads it?
humor_imagesImage path, owner, title, description, attribution.Owner; public metadata for ready runs.
humor_runsState, pair A/B, image, request key, retry parent.Public ready comparisons; owner reads their unfinished runs.
humor_votesOne user/run choice.User reads their own row. No general access to everyone else's votes.
private.humor_run_detailsStage traces, result, attempt token, baseline slot.Restricted database functions. Poll returns the slot mapping only after the caller's vote.

Row-level security (RLS) is the database rule system that limits which rows a caller may read. Grants first determine whether a role can access a table or function at all. The vote table's primary key (run_id, user_id) allows one row for each person and comparison. Direct inserts/updates are not granted to the browser's role.

humor_vote derives identity from the authenticated session, checks A/B and a ready run, then inserts with ON CONFLICT DO NOTHING. It returns humor_poll in the same transaction. A repeated request keeps the first saved choice even if its new payload asks for the other slot.

The private poll function checks that this user has a vote on this run before counting all rows and returning baseline_slot. Its SECURITY DEFINER privilege lets it aggregate beyond the caller's own RLS-visible row. That power is bounded by explicit identity checks, restricted execution grants, an empty fixed search_path, and qualified table names. The public RPC wrapper uses the caller's privileges to invoke this narrow operation.

05 / The full project: supply a usable comic move

Retrieve a situation, then adapt its mechanism.

Retrieval-augmented generation (RAG) supplies selected external records to a model before it writes. In this project, a retrieved joke can provide an association or a humor mechanism: the way its setup turns into a surprising interpretation. The goal is to transfer that move to the image while keeping the visible evidence.

A search for “cat” may return animal puns unrelated to sleep or work. A search for “being present at work while doing nothing” can find a useful workplace situation with no cat words. This is why the full plan stores the situation, expectation, twist, mechanism, and entities separately. These are model-generated interpretations to review, not objective facts supplied by the original author.

An association path is an ordered series of related ideas with a known visual root. Recording each relation lets you inspect why an office joke entered a cat caption. Retrieval can broaden the model's choices; it can also introduce irrelevant premises, copied punchlines, or prompt instructions hidden in data. Bound and validate retrieved text, keep its source IDs, and never let it change the system's instructions.

How the planned search combines two signals

Lexical search matches words through Postgres full-text search. Dense search compares embeddings: fixed-length numeric vectors produced by a model so related text can have similar representations. The plan starts with a pinned revision of all-mpnet-base-v2, normalized 768-dimensional vectors, and two fields per joke: situation/setup and mechanism/twist. A full-joke embedding is the simpler comparison.

For normalized query vector q and document vector d, cosine similarity is their dot product Σ qᵢdᵢ. Higher similarity means closer representations; it is not a humor score. Ingestion and query encoding must use the same model revision and preprocessing.

Reciprocal rank fusion (RRF) combines ranked lists without assuming that their raw scores share a scale. A record contributes once from each active list in which it appears. With equal channel weights and smoothing constant 50:

RRF(j) = Σlists containing j 1 / (50 + ranklist(j))
Ranks start at 1; an absent record contributes 0.

Apply corpus revision, language, allowed-use, and train-only filters inside each search before choosing its top results. Filtering only after the top five can leave no eligible evidence even when good records existed below them. Start with exact vector scans so you have a correctness reference. Add HNSW, an approximate graph index that speeds nearest-neighbor search, only when measured latency warrants it. Under filters, check missed neighbors and too-few results against exact search.

The seven-call product adaptation

  1. Scene call: objects, actions, expressions, relations, text, distinctive detail IDs, uncertainty.
  2. Conflict call: up to three supported oppositions or clearly labeled analogies.
  3. Two association calls: one views the image, one uses its description. Locally merge and deduplicate them before retrieval.
  4. Merge/path-selection call: use retrieved evidence and pruned associations to select useful paths.
  5. Generation call: write five distinct caption candidates from different paths or mechanisms.
  6. Judgment call: check grounding and copying, rank candidates, and return up to three acceptable captions.

There are seven successful calls because step 3 contains two. The proposed ceiling is ten attempted model calls including retries and a single schema repair. Two targets with at most three hops give at most 2 × (1 + 3) = 8 root-and-hop queries. At five hits per query that is at most forty pre-deduplication hits; cap the final unique jokes at twenty and initial demonstration text at 1,500 tokens. A token is a model's text unit, not always a word.

Bounded paths make cost, inspection, and prompt size manageable. The planned records retain each node's origin, evidence IDs, retrieved source IDs, candidate path, acceptance decision, and usage. A failed stage yields a failed or explicitly degraded run. It must never become a made-up successful caption record.

Understand HOMER pruning and the reference modes

HOMER prunes, or removes, weak retrieved associations. The paper adds a relatedness/opposition term, a frequency term, and a part-of-speech diversity term. WordNet, a lexical relation database, supplies the word relationships. These are ranking heuristics; their sum is not the probability that a caption will be funny.

H = Hrel + Hfreq + Hdiv
Hrel = s + s·exp(−s)·o

Here s is semantic relatedness and o is lexical-neighborhood dissimilarity, each between 0 and 1. With s=0.6 and o=0.8, the term is about 0.8634. With s=0, the opposition bonus is zero. This keeps an unrelated word from receiving a bonus just because it is different. Lexical dissimilarity is only a proxy for a useful opposition.

The paper's frequency term is the square root of token-frequency share times joke-coverage share. The diversity term is the fraction of the part-of-speech inventory represented. A noun/verb ambiguity can offer wordplay; frequent or ambiguous words can still be unfunny.

The inspected release retrieves the first five substring hits when enough exist; otherwise it fits TF-IDF to the query before transforming the corpus. TF-IDF weights words by frequency and rarity. The release also uses a root-to-association graph rather than the paper's sequential paths, and an active TF-IDF frequency component rather than the paper's frequency formula. The planning audit counted eight demo calls, versus seven reported in the paper.

Keep release reference for observable released behavior, paper reference for the published equations/paths, and HumorLLM for the bounded product changes. Record model and data substitutions. The current three-call MVP is a separate, smaller prompt-chain experiment.

06 / Data design protects both quality and interpretation

Keep the library, the workshop, and the test separate.

The retrieval library supplies examples during generation. The development set is where you inspect failures and tune choices. A held-out set stays untouched until you freeze the system and measure it. If the same contest, image variant, or answer caption appears in more than one role, data leakage can make the system seem better than it is.

One identity across encodings

Group records by contest ID and near-duplicate image cluster before splitting. A different JPEG encoding changes a file hash without making a new scene. Keep all captions and explanations for that contest in its one assigned group.

One auditable library record

Keep original joke text, source ID, allowed-use metadata, normalized hash, duplicate group, annotation version, and embedding revision. Store setup and punchline together so retrieval preserves the joke's turn.

The plan found 251 contest IDs shared by two downloaded image collections, even though their file hashes differed. This is a recorded planning finding, not a fresh recount here. Grouping prevents leakage introduced by our pipeline; it cannot establish what the underlying foundation model saw during its original training.

Why two embeddings have a real storage cost

Float32 uses four bytes per number. For two 768-dimensional vectors and N jokes, raw values use N × 2 × 768 × 4 bytes. For 10,000 jokes this is 61,440,000 bytes, or 61.44 decimal MB (58.59 MiB). For 44,480 jokes it is 273.29 MB. Text, row overhead, indexes, replicas, and backups add more.

Supabase stores vectors; it does not produce these embeddings automatically. The Python component must encode both the library and future queries using the same frozen encoder. Start small, inspect database capacity, and scale only after retrieval is useful.

The planned image pools and what each buys
  • 10 training cartoons: a technical smoke set to exercise end states, with separate bad-input fixtures.
  • 40 development images: 20 training cartoons and 20 natural-photo/meme inputs for debugging.
  • 47 official test cartoons: primary held-out cartoon report; do not tune on these outputs.
  • Up to 53 additional cartoons: exclude overlapping contests and report separately.
  • 100 locked product images: natural/reaction inputs to test transfer to the actual upload domain.

These are proposed allocations. Human reference captions are useful for some protocols; fresh pairwise preference judgments can compare two systems on the same image without reference captions. Put inputs with existing text in a separate stratum and forbid copying their overlays.

Separate humor, relevance, and usability

Hide method labels and randomize presentation order. Ask independent raters from the stated audience whether each caption fits the image, which is funnier, and whether either is worth using. Allow tie and neither. “Neither” can be neutral for relative preference while indicating that both outputs failed the product's purpose.

Preference score = (wins + 0.5 × ties + 0.5 × neither) / all comparisons

Here wins favor the tested system; losses contribute zero. Ordinary ties and “neither” are distinct saved categories. This score treats them equally for relative comparison, while usability and the neither rate keep their difference visible.

Can a higher preference score hide an unusable product?

Try increasing “neither.” Both captions become unusable on more comparisons even though each “neither” still contributes 0.5 to relative preference.

12 wins + 4 ties + 2 neither + 2 losses → (12+2+1)/20 = 0.75; neither rate 10%. A second set with 2 wins + 18 neither gives (2+9)/20 = 0.55, while 90% of comparisons have no usable option. The first set's absolute usability is still unknown without separate judgments.

A confidence interval expresses uncertainty in an estimated outcome. Repeated votes on one image share the same output pair, so they are not independent new image cases. Cluster bootstrap resamples images or template groups, retaining their ratings together. Treating every rating as an unrelated image can make the result look more certain than it is.

The plan proposes a 95% interval entirely above 0.50 against the direct baseline, plus a lower confidence bound on visual-relevance change above −5 percentage points on product images. These are proposed gates; sample sizes may be too small to pass. Failure to establish improvement should lead to an uncertainty statement and further independent images, not tuning on the same held-out set.

Check the planned evaluation arithmetic

Development: 40 images × 3 raters × 3 comparisons against B0 = 360 judgments. Frozen main evaluation: (47 cartoons + 100 product images) × 3 raters × 2 comparisons = 882 judgments. The two comparisons pair the selected system with B0 and B1. Optional supplemental cartoons are outside that 882 count. Report cartoon and product outcomes separately.

Track relevance, selected-caption preference, usable top-three rate, repetition, copied punchlines, unsupported premises, failures, latency, and cost per successful image. Count failed generations in operational results. Record repeated rater tasks to assess consistency, while preserving image-level dependence.

Why pass@5 and an LLM judge cannot replace this test

Pass@k asks whether a sample of k candidates contains at least one that beats the reference under the chosen judgment protocol. If an image has 5 candidates and 2 beat the reference, its pass@1 is 2/5=0.4. Pass@3 is 1 − C(3,3)/C(5,3) = 0.9, where C(n,k) counts ways to choose k items. Neither figure tells you whether your selector delivered a winning caption.

A model judge can help diagnose or rank outputs, but may prefer particular wording or orders. Calibrate it against human pairs and swap caption order. Keep its outcomes separate from human preference. A selector trained on one judge and evaluated only by the same judge can learn that judge's preferences. Lexical overlap scores also do not directly measure funniness.

Why the full plan adds Python and a worker

A worker is a separate process that claims jobs and continues independently of the browser's HTTP request. Python suits data preparation, embedding models, and experiment scripts. The app would enqueue a job in Postgres, return its ID, and let the browser poll an authorized status route while the worker extracts, retrieves, generates, and ranks.

A lease is a time-limited right to process a job. A worker extends it with a heartbeat and saves stage checkpoints. If it crashes, another worker claims the expired lease and resumes completed stages. An attempt identifier must reject late writes from the old worker. Where Colab, an L4, and preference learning belong

The initial hosted-API system does not need a GPU. Colab can help batch annotation and embeddings, but a variable notebook session is unsuitable as the app's dependable backend. Colab access does not include Gemini API credit.

An NVIDIA L4 is an optional qualification for a pinned Qwen3-VL-8B-Instruct configuration if measured cost, privacy, rate limits, or latency justify local inference. Start at batch size 1, bounded resolution, and an 8k total context budget with a supported 4-bit runtime. Quantization stores model values with fewer bits to reduce memory; it can affect quality and does not guarantee fit. Verify driver/CUDA and inference-process visibility before loading. Compare the same 20 development images. Preserve failures, do not silently change the target, and stop/verify the VM before retrieving results. The proposed first window is at most two hours plus an explicitly set dollar cap.

If selection becomes a demonstrated bottleneck, begin with roughly 1,000 real A/B preferences across at least 100 image/template groups and a 200-pair training pilot. A small ranker or cross-encoder can score scene/caption pairs. LoRA, a method that trains a small set of additional model parameters, is a later option. Training a selector cannot create a good candidate when none exists.

2. Reconstruct the critical request path

A user uploads an 8,000 × 6,000 image. Name the size boundaries, the authorization checks, the expensive-work claim, and the final publication step.

Hint for the request trace
Browser → action → storage/database → generation route → private step records → finish.
Answer and reasoning

48 million source pixels are reduced by the browser to fit a 1,600-pixel longest side, giving 1,600 × 1,200 for this aspect ratio, with output at most 2 MiB. The 3 MB transport limit is checked before the action body runs. The action requires a verified complete profile and sharing acknowledgment; Sharp validates/re-encodes before saving. A request key identifies the pending run. The generation route checks origin, session, UUID, and ownership, claims with the writer key, and prepares a shared ≤1,200-pixel provider image. Gemini stages are awaited and recorded. The database finish transaction saves metadata, both captions, private mapping, and ready status together.

Resizing a 48-MP source in this path is an implementation capability, not proof that every large file will decode or compress successfully.

5. Interpret a promising result

A trial has 12 wins, 4 ties, 2 neither, and 2 losses. All twenty judgments concern only two images. Calculate preference and neither rate. Explain why twenty ratings are weak evidence of image-level generalization.

Hint for the calculation
Use 0.5 for each tie or neither. Count independent image groups separately.
Answer and reasoning

Preference = (12 + 0.5×4 + 0.5×2)/20 = 0.75. Neither rate = 2/20 = 10%. Only two image cases produced the caption pairs; ratings share those outputs. A confidence interval based on twenty independent images would overstate the evidence. Collect more independent image/template groups, use group-based uncertainty, and inspect separate relevance/usability judgments before a release claim.

6. Recover from a worker crash

In the planned full system, scene extraction and retrieval are saved. The provider finishes generation, but the worker crashes before saving that response. What can a replacement worker reuse? What cost uncertainty remains?

Hint for recovery
A saved checkpoint and an external provider side effect are different facts.
Answer and reasoning

After lease expiry, a checked claim gives the new worker authority. It can reuse valid scene and retrieval checkpoints under the same image/model/prompt/corpus/embedding versions. The unsaved response cannot be assumed recoverable; another generation call may be required and charged even though the first also succeeded. Mark the ambiguous attempt and guard late writes with the attempt identity. Do not overwrite a ready pair or duplicate votes.
